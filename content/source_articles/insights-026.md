## 요약

Anthropic이 Claude Opus 5, Claude Fable 5 같은 신세대 모델을 위해 Claude Code의 시스템 프롬프트를 80% 이상 줄이면서도 코딩 평가 성능에 손실이 없었다는 내용의 글. 모델이 똑똑해질수록 컨텍스트 엔지니어링의 원칙도 바뀌어야 한다는 것이 핵심 메시지.

## 왜 시스템 프롬프트를 줄였나

- 실제 사용 로그를 보면 시스템 프롬프트, 스킬, CLAUDE.md, 사용자 요청이 서로 충돌하는 지시를 내리는 경우가 많았다. 예: "필요하면 문서화해라" vs "절대 주석 달지 마라".
- 예전에는 최악의 시나리오(파일 삭제 등)를 막기 위해 강한 규칙을 넣어야 했지만, 이제는 모델이 맥락과 판단력으로 이를 대체할 수 있다.
- Claude Code에는 이제 메모리, 아티팩트, 스킬 등 더 많은 도구가 있어서, CLAUDE.md 하나에 모든 것을 담을 필요가 없어졌다.

## 예전 방식에서 지금 방식으로 바뀐 5가지

1. 규칙을 준다 → 판단에 맡긴다
   과거에는 "주석 쓰지 마라", "멀티라인 docstring 금지" 같은 강한 규칙을 줬지만, 지금은 "주변 코드 스타일에 맞춰라" 정도로 충분하다. 모델이 상황별로 옳은 결정을 더 잘 내리기 때문.

2. 예시를 준다 → 인터페이스를 설계한다
   예시를 주는 것은 오히려 모델의 탐색 범위를 좁힌다. 대신 도구나 파라미터 자체를 더 명확하고 표현력 있게 설계하는 게 낫다. 예: Todo 도구의 상태값을 pending/in_progress/completed로 열거형화하면 그 자체가 사용법에 대한 힌트가 된다.

3. 처음부터 다 준다 → 점진적 공개(progressive disclosure)를 쓴다
   코드 리뷰나 검증 방법처럼 항상 필요하지 않은 정보는 별도 스킬로 분리해서 필요할 때만 불러오게 한다. 도구도 마찬가지로, ToolSearch로 필요할 때만 전체 정의를 불러오는 지연 로딩 방식을 쓴다. CLAUDE.md나 Skill.md도 하나의 거대한 저장소로 만들기보다 여러 파일로 나눠 필요한 시점에 로드되도록 트리 구조로 구성하는 것이 좋다.

![Claude 스킬의 점진적 공개 구조를 3단계 피라미드로 나타낸 도식](</figures/insights-026/web-2.jpg> "Claude 스킬이 내용을 단계적으로 불러오는 방식을 보여 주는 도식이다. 이름·설명 같은 메타데이터(약 100바이트)는 항상 로드되고, SKILL.md 본문(약 2~5KB)은 스킬이 요청과 맞을 때 로드되며, 스크립트·템플릿·참고 문서는 지시문에서 참조할 때만 불러온다. 출처: aiagentskit.com")

4. 반복해서 말한다 → 도구 설명은 간단하게 쓴다
   예전 모델은 지시를 반복해야 하거나 컨텍스트 끝부분의 지시를 더 잘 따르는 경향이 있어서 시스템 프롬프트와 도구 설명에 같은 내용을 중복 기재했다. 이제는 중복을 없애고, 도구 사용법은 도구 설명 안에만 넣으면 된다.

5. CLAUDE.md에 메모리를 쌓는다 → 자동 메모리를 쓴다
   예전에는 # 단축키로 CLAUDE.md에 수동으로 기록하도록 유도했지만, 이제 Claude가 관련 있는 내용을 알아서 자동으로 기억한다.

(추가: 심플한 스펙 → 풍부한 참조자료)
   plan 모드에서 마크다운 계획 파일에 의존하던 방식에서, 이제는 HTML 아티팩트, 코드, 테스트 스위트, 루브릭(rubric) 같은 더 정교한 참조자료를 활용할 수 있다.

## 컨텍스트를 구성하는 4가지 층

- 시스템 프롬프트: 제품 맥락에 종속. 자체 에이전트 하네스를 만드는 경우 가장 공들여야 할 부분.
- CLAUDE.md: 가볍게 유지하고, 레포가 무엇인지 간단히 설명한 뒤 코드베이스의 함정(gotcha) 위주로 채운다. 파일 시스템만 봐도 알 수 있는 당연한 내용은 넣지 않는다.
- 스킬: 필요할 때 찾아볼 수 있는 가벼운 가이드로 취급. 과도하게 규칙을 강제하지 말고, 팀/제품 고유의 의견이나 노하우를 담을 때 가장 효과적이다.
- 참조자료: @ 멘션으로 파일을 포함시켜 심화 정보를 제공. 설명이나 스크린샷보다 코드나 HTML 목업처럼 고충실도의 참조자료가 더 나은 결과를 낸다.

## 개인 적용 포인트

- 지금 쓰고 있는 글로벌 CLAUDE.md/rules 파일들(FastAPI 패턴, 스타일 가이드 등)이 혹시 과도하게 규칙화되어 있지는 않은지 점검해볼 만하다. 신세대 모델은 예시나 강한 규칙보다 잘 설계된 구조와 맥락만으로도 판단을 잘한다.
- Obsidian 스킬/CLAUDE.md 구조도 점진적 공개 원칙에 맞게 트리 구조로 나뉘어 있는지 다시 볼 필요가 있음.
- `claude doctor` (/doctor 명령어)로 스킬과 CLAUDE.md를 자동으로 점검, 슬림화할 수 있다고 하니 한 번 사용해볼 것.
